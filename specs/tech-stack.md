# Tech Stack

## Hard requirements (hackathon qualification)

These are non-negotiable — the submission does not qualify for prizes without them:

- **Sabre travel APIs** for all travel data and booking operations (flights, stays, ground transport, dining, experiences).
- **Vocal Bridge** as the voice layer.
- The demo shape is fixed by the challenge: **one voice agent, one conversation** — flights, stays, ground transport, dining, experiences and more pulled into a **single itinerary**, booked and managed by voice.

The team's locked demo concept (Cascade Repairer — see `mission.md`) maps the five required categories as: flights → Sabre rebooking, stays → Sabre hotel change, ground/dining/experiences → simple mock tools.

**Entitlement reality (Phase 25 CERT exploration, 2026-07-13; matrix completed by Phase 26, 2026-07-14):** the hackathon developer credentials give **real shopping, mock booking** — Flight Search API v1 (InstaFlights) returns real priced itineraries, but `createBooking` is entitlement-blocked (`PassengerDetailsRQ` unauthorized) and the PCC has no BFM air content. The Phase 26 close-out finished the sweep with executed classifications: `modifyBooking` **is authorized** (dummy-PNR business error — the wall is create-side only), Flight Reshop and EnhancedSeatMap (POST, v3.0.0) are entitled but schema-uncracked, air availability and exchange shopping are not entitled, and schedules/car have **no REST endpoints** on CERT (SOAP-only domains — the mock ground leg stays). One shape precision that tripwires depend on: the entitlement wall's `UNAUTHORIZED_ACCESS` marker lives in the error's `type` field (`category` is `UNAUTHORIZED`). Full matrix: `specs/2026-07-13-sabre-cert-exploration/sabre-cert-notes.md`.

**2026-07-14 evening addendum (Phase 27 shipped; live probes the same day):** three findings sharpen that posture. (1) InstaFlights is **cache-based** (Travel Insight) with **per-pair advance-purchase windows**: on 2026-07-14, **113 of the 731 supported US pairs had real content at +2 days** (e.g. SFO→MIA, SEA→BOS, JFK→LAX, DFW→EWR) while others start at +30 days; empty results arrive as a documented **HTTP 404 "No results were found"**, not an empty 200 (since Phase 28 the real client strict-matches that body — `WARN.RAF.APPLICATION` code first, message fallback — and returns an honest empty, so the agent speaks the no-flights line instead of mock-swapping), and the pair menu shifts when the cache refreshes **and as the UTC day rolls** (observed 2026-07-14 evening: a date with morning content emptied once 00:00 UTC — 5 PM PDT — made it +1 day, below the pair's minimum advance-purchase window; evening rehearsals cross that boundary). (2) Sabre's new agentic `/v1/offers/*` family (flightShop — BFM's replacement — and flightShopLite) is **entitled but content-empty on this PCC** (HTTP 200, zero offers), and the official Sabre **MCP Server** pilot (CERT-only, ~7-day activation) is permission-aware — it cannot bypass entitlements. (3) **Decision (2026-07-14): no entitlement ask to Sabre** — the ask route is closed; the demo is designed entirely within current credentials. Posture: every *shopping* surface (guided booking **and** the flight-repair re-shop, roadmap Phase 29) speaks real InstaFlights data on near-term-cached pairs; every PNR *write* stays mock for this hackathon, permanently.

**2026-07-15 addendum (Phase 30 replan — the cached set is thin and decays fast):** the 113/731 +2-day figure above was a **single-day snapshot, not a standing menu**. Live re-probing on 2026-07-15 (against the deployed service) found the 2026-07-14 demo shortlist largely emptied — of SFO→MIA / SEA→BOS / DFW→EWR / JFK→ORD / MCO→JFK / … only **JFK→LAX** returned priced content, and it alone held across every date probed (+2 through +30), making it the current **verified-reliable demo anchor**. Content shifts hour-to-hour and per-pair (a pair green in the morning can empty by afternoon), so a multi-day-old sweep proves nothing about demo time. Two operational consequences: (1) the demo must **pin a morning-verified pair** and re-probe minutes before presenting — `README.md` now documents the day-of `/v1/web_call/query` probe loop (the manual form of the Phase 24/29 morning-smoke; use a **unique** `session_name` per call — a reused/collapsed name makes the agent replay prior options instead of searching); and (2) the CERT priced-search tripwire (`test_sabre_cert.py::test_instaflights_search_returns_real_priced_itineraries`) hardcodes a single pair/date (DFW→LAX +30d) and so **reds on cache drift alone** even when the code is healthy (proven 2026-07-15: DFW→LAX +30d honest-empty while JFK→LAX +30d returned real fares through the identical path) — a known brittleness, Phase 24 candidate.

**2026-07-16 addendum (Phase 35 QA follow-up — the return direction is closed on InstaFlights):** probed from the real client's exact request path the same day Phase 35 shipped: the reverse pair (LAX→JFK) is honest-empty at every probed date (+10 through +30 days), and **round-trip `returndate` searches are equally dead** — 404 no-results at every date *including* the anchor July 21→23, while the same-run one-way JFK→LAX control returned 3 itineraries (round-trip requires both directions cached, so it inherits the empty reverse pair). Consequence: **"can I get back?" answers ride Tavily web search** (roadmap Phase 34, re-scoped that day — a spoken *indication* that return flights exist, never presented as searched fares or bookable inventory; proven answer quality: "Three airlines operate nonstop flights from LAX to JFK on July 26, 2026: JetBlue, American Airlines, and Delta Air Lines"). ## Voice layer

- **The demo's primary surface (re-settled by Phases 22–23, live-QA'd 2026-07-15) is the one-page cascade dashboard**: `GET /v1/cascade/` carries the complete book → break → consent → repair → callback contract. The center-column **voice orb** is the booking surface (the `web_call` wiring — server-minted token, `useAIAgent → /v1/web_call/query` delegation, connection/latency states; the pinned VB CDN versions are injected at serve time from `web_call.py`, the no-drift rule), flanked by the traveler/Cascade conversation feed, the Phase 22 repair surfaces, a Sabre live-search panel (dispatcher ring buffer behind gated `GET /v1/sabre_tools/search_log`), and the consent treatments — red "waiting for the traveler's go-ahead" with **no running clock** between break and consent, the 60-second recovery timer anchored at the spoken yes, stand-down + re-armed Cancel on declined/timeout. A **🆕 New trip** control gives the booking beat a clean slate: it clears the displayed trip AND ends the live voice session (sessions pin to the displayed trip — without this, guided booking is unreachable, the Phase 18 trap rebuilt client-side), and the page re-adopts only a *newly booked* trip. Quota: 2 calls per full run (booking is web-voice, free). The two-button page (`GET /v1/demo/`) is demoted to a backup operator surface; the **Vocal Bridge web client** (`/v1/web_call/`) remains the L3 reference surface and the clean *unpinned* booking fallback (it deliberately sends no trip pin). The README carries the operator run sheet ("Running it live").
- **Headless mobile voice page (Phase 16): `GET /v1/mobile_voice/`** — the web_call page's VB wiring with no visible DOM, built for the iOS app's hidden webview (see § iOS app). Same pinned CDN versions (imported from `web_call.py` so they can never drift), same server-minted token (`POST /v1/web_call/token`), same `useAIAgent → POST /v1/web_call/query` delegation — so the Concierge, session memory, and turn logging behave identically across web and app, and every Concierge upgrade is testable in a desktop browser before iOS is involved. Events no-op to `console.log` when `window.webkit` is absent, keeping the page smoke-testable outside the app shell. Since Phase 19 both this page and web_call hold the displayed trip (`?trip_id=` seeded, `window.vbSetTrip()` updated by native) and send it with every `/query` POST; the mobile page **only** additionally carries a `TEMP bridge` — a self-fetched `/v1/sabre_tools/latest_trip_id` as the lowest-precedence `trip_id` (vbSetTrip → `?trip_id=` → bridge; a failed fetch silently omits it) so the in-review App Store binary is trip-aware from a backend deploy alone. Remove with BACKLOG Phase 20 (v1.0.1); web_call deliberately has no bridge so desktop rehearsals keep a clean unpinned default. **Rehearsal path stays `/v1/web_call/` + the `/query` seam via curl — no outbound-call quota spent.**
- **Vocal Bridge account constraints (learned the hard way, 2026-07-10):** outbound calling exists only on the **Developer plan and up** ($49/mo) — Free/Starter include none, and the DeepLearning.ai partner grant's 10-call pool is spent and never refills. Quota: **10 outbound calls/day and 10 call evals/day, resetting 00:00 UTC** (5 PM PDT the prior evening, so event day gets a full quota). Callee numbers must be verified in the VB dashboard. Timing: `place_call` blocks ~10–16 s until the call is queued, and the phone rings ~10–15 s after that — a full two-beat demo run costs 2 calls.
- **"Testing Vocal Bridge" smoke-test page** (roadmap Phase 4): a minimal FastAPI-served page that makes a real Vocal Bridge call (per the training-course lessons) using the API key already set on Cloud Run — de-risks auth, call shape, and latency before any voice architecture is built.
- **Live itinerary UI — shipped 2026-07-09 (Phase 10)**, the demo's second surface: `GET /v1/itinerary/` serves a self-contained static page (`backend/api/assets/itinerary/page.html` — vanilla HTML/CSS/JS, no build step, no external requests; read per request because `uvicorn --reload` only watches `.py` files) that **polls** `GET /v1/itinerary/status/{trip_id}` every 1.5 s. The screen flipping **broken → repairing → fixed** while the agent talks is the demo moment: five status cards (all six lifecycle statuses have visual hooks), a traveler-voiced repair feed derived client-side by diffing statuses between polls (no server-side event state), a recovery timer against the 60-second target, and a trip selector backed by `GET /v1/itinerary/trips` (`list_recent_trips` in the trips repository; since 2026-07-12 the payload carries `created_at`, and the selector labels each trip with its creation time in "PT" and sorts newest-first client-side). The status payload (`trip`, `items`, `summary.counts`/`all_clear`, `fetched_at`) is deliberately UI-agnostic so Phase 12 rehearsal scripting and eval capture reuse the same endpoint; since Phase 17 items with a booking additionally carry an **additive, best-effort `detail` object** (`why_chosen`, `price_delta`, `impact` — derived from the latest booking's `raw_response`, omitted when there's nothing to say, and a failed bookings read can never break the poll) feeding the iOS recommendation sheet — the web page ignores it; since Phase 32 a flight-repair booking also yields a **`rebooked_from` was-line** ("Was Delta 439 · departed 8:05 AM PT · $214", degrading to clock/price when the original had no stamped identity), which the cascade page renders struck-through under the rebooked flight's headline fields; since Phase 33 the flight item's `details` carries the **rich fields** (`airline_name`, `cabin`, `duration_minutes`, `layover_airports`, `arrives_next_day`, `stops`) which the cascade card renders as a carrier headline plus a terse facts row — each part hidden when its field is absent, so pre-33 trips render exactly the pre-33 card. Standing decisions (validation triage 2026-07-09): no browser-automation test dependency — the page's JS behavior is scripted manual QA; deep-linking `?trip_id=` to a trip outside the recent-selector list works but is an unsupported, untested contract.
- **Voice booking page — shipped 2026-07-12 (Phase 21), the pre-disruption beat's surface**: `GET /v1/booking/` serves a self-contained static page (`backend/api/assets/booking/page.html`, thin router `backend/api/booking_ui.py`) built on the itinerary page's *technical* conventions (no build step, per-request HTML read, `?code=` → `localStorage` → `X-Access-Code`, shell on the access-gate allowlist) but styled to **`about/ui_ideas/ui_mockup_2026_07_09.png`** — the design source of truth this page shares with the Phases 22–23 dashboard: app header (product name, current traveler, booking-beat status pill), left rail (traveler-context card, trip timeline with per-leg status icons, collapsible recent trips), prominent current-flight card (+`detail` fields), four reservation cards with the six-status hooks, and a right-column candidates panel on the mockup's "AI Recommended" card treatment (the center voice column and repair surfaces are deliberately absent — Phases 22–23). Driven entirely by the 1.5 s status poll; honors the `?trip_id=`/`window.vbSetTrip()` pinning contract and re-resolves `GET /v1/sabre_tools/latest_trip_id` every 4 s, adopting a **change** in the answer so a trip booked mid-conversation appears without a reload (the iOS `TripManager` pattern). Its data rides on an **additive, best-effort `pending_options` block** on `GET /v1/itinerary/status/{trip_id}` (the `detail` precedent — omitted when there's nothing to say, a failure can never break the poll): `search_flights_impl` records `(session_id, options, recorded_at)` into a module-level latest-search slot in `concierge.py`, `book_flight_impl` clears it on success, and the status endpoint surfaces it (numbered options — route, PT time labels, rounded prices, and since Phase 33 `airline_name` + formatted `duration`: carrier *names*, never codes) when the slot's session is pinned to the requested trip **or unpinned** (the pre-booking window; with two simultaneous unpinned conversations another trip's poll could briefly show the other session's candidates — accepted single-operator demo looseness). Known residual (Phase 21 validation report), narrowed by Phase 30: `search_flights_impl` now clears both `_SESSION_FLIGHT_OPTIONS` and its **owned** `_LATEST_SEARCH` slot on every *non-optioned* return (no-results, error, unsupported market, missing input, ownership-guarded like `book_flight_impl`), so a traveler told "no flights" can no longer book a stale choice; what remains is the **age/abandonment** expiry — a conversation that got real options and never booked still leaves them visible until its next search or booking — which rides with roadmap Phase 22.
- All three course architectures live in the codebase as working reference implementations, ported from the L2–L5 notebooks in `jupyter_notebook/training_course/`:
  - **Cascaded stack** (STT → LLM → TTS) — easiest to debug.
  - **Real-time voice-to-voice** — lowest latency (200–500 ms).
  - **Hybrid "Concierge"** — fast foreground agent for turn-taking/fillers, background agent for deep reasoning and tools. Target architecture for the demo.

## iOS app — Talk to My Trip (shipped 2026-07-11, Phase 16; submitted to App Review 2026-07-11 — approval is a bonus, not required for event day; never upload a new binary until this one is approved)

- **`ios/TalkToMyTrip/` — native SwiftUI app** (iOS 17+, iPhone-only, portrait, **zero third-party dependencies** — SwiftUI + WebKit + AVFoundation only), conventions mirrored from `example_project/ios_assessor` (actor `APIService`, `APIConfig` environment switch, `@Observable` Manager pattern). `ios/` rides along untouched by Cloud Build — **no CI for the app**; build verification is Xcode-local (`xcodebuild` works headlessly; the project uses Xcode 16+ file-system-synchronized groups, so new Swift files need no pbxproj edits).
- **Voice transport is the hidden-WKWebView bridge** (locked in `IOS_PLAN.md`, proven in Phase 16): a 1×1pt, opacity-0 webview that must stay **in the view hierarchy** (detached webviews get throttled) loads the headless `GET /v1/mobile_voice/` page over HTTPS (required for `getUserMedia`). Native ⇄ webview contract: native drives `window.vbConnect()`/`window.vbDisconnect()` via `evaluateJavaScript`; the page posts JSON events `{type: state|transcript|reply|error}` to the `"vb"` `WKScriptMessageHandler`. Mic permission is requested **natively first** (`AVAudioApplication`), and `WKUIDelegate.requestMediaCapturePermission → .grant` suppresses the webview's second prompt — exactly one system mic prompt.
- **Trip state is polling, not push**: `TripManager` polls `GET /v1/itinerary/status/{trip_id}` every 1.5 s (the same UI-agnostic contract the web page uses), re-resolves `GET /v1/sabre_tools/latest_trip_id` on session start **and after every agent `reply` event** — so a trip the agent books mid-conversation appears without an app restart — and diffs item statuses between polls to drive card animations and the 60-second recovery timer. Since Phase 19 the displayed trip also reaches the voice session: `APIConfig.mobileVoiceURL(tripId:)` seeds `?trip_id=` and `VoiceManager.setTrip` forwards every `TripManager.tripID` change to the page via `window.vbSetTrip` (closing the race where the webview loads before cold-start trip resolution) — the server pins it only if the session has no pin yet.

A **first-use consent sheet** (guidelines 5.1.1/5.1.2) names Vocal Bridge/OpenAI/Google Cloud before the mic ever activates, with a real decline; consent is withdrawable from the About sheet (ends the live session). Bundle id `com.zensoftware.talktomytrip`, SKU same, Apple ID `6789972026`, Zen Software org (`M59U69URHH`). The full submission runbook is **`IOS_DEPLOY.md`** at the repo root.
- **Access gate on device (Phase 17)**: first launch shows a one-field gate validated against `POST /v1/auth/validate`; the code lives in the **Keychain** (`KeychainHelper`), every `APIService` request carries `X-Access-Code`, and the webview loads `/v1/mobile_voice/?code=…`. ## Backend

- **Python / FastAPI** (`backend/`), containerized with Docker; local orchestration via `docker-compose.yml` and the `Makefile`.
- **OpenAI Agents SDK** for the agentic LLM layer — agents, tools, handoffs, and MCP servers, following the pattern in `backend/api/hello.py`. OpenAI models serve as the reasoning engine (not Anthropic, deliberately diverging from the course's LLM choice).
- **MCP servers** (`backend/mcp_servers/`) expose tools to agents — e.g., the filesystem server, plus Sabre-backed tools as they're built.
- **Sabre APIs — shipped 2026-07-08 (Phase 6)** as a client layer in `backend/api/sabre/`: pydantic shapes (`shapes.py`) tracing 1:1 to a live docs pull (`specs/2026-07-08-sabre-tools/sabre-api-notes.md` — Bargain Finder Max v5 for search; Booking Management `createBooking`/`cancelBooking`/`modifyBooking` for book, cancel, and hotel date change; **rebook has no single REST endpoint** — it composes cancel + create, the documented unticketed-PNR path), a deterministic mock client returning those shapes, and a real client (needs `SABRE_BASE_URL` + `SABRE_CLIENT_SECRET` — the composed Basic secret; derivation from the raw `config/.env` pair is documented in the Phase 25 notes). **CERT-certified 2026-07-13 (Phase 25)** with findings: v2 client-credentials auth works (7-day token, refetch on 401); BFM v5 processes only with a POS block and no IntelliSell `RequestType`, and returns no inventory on this PCC; `createBooking` is entitlement-blocked; and three latent client gaps are pre-scoped as the conditional Phase 24 punch list (dead `POS` field in `shapes.py`, required-but-omitted lists on empty BFM responses, Booking Management failures arriving as HTTP 200 + `errors[]`). Re-runnable probes live in `specs/2026-07-13-sabre-cert-exploration/probes/`. The runtime flag is the **`SABRE_MODE` env var** (`mock` | `real`, default `mock`), read **per call** by the dispatcher (`client.py`): in `real` mode any failure auto-falls back to the mock **for that call** and logs a warning naming the operation — with one deliberate non-failure (Phase 28): the documented InstaFlights no-results 404 returns an empty response from the real client, so a merely-empty date speaks the honest no-flights line and never mock-swaps. A 401 clears the cached token and retries once with a fresh one before falling through (Phase 28 — survives the 7-day token expiry and credential resets without a restart). Flipping it on Cloud Run is an `--update-env-vars` merge — no rebuild. Judges see the same cascade either way. The **six repair tools** (`backend/api/repair_tools.py`, OpenAI Agents SDK `function_tool`s — three Sabre-backed, three category mocks) each write a `bookings` row (Sabre payload as `raw_response`) through the repositories and raise on failed/0-row writes; the cascade unit owns the status flips. **The flight repair additionally rewrites its `itinerary_items` row (Phase 32)** — the rebooked flight's PT timestamps (via the shared `flight_options.option_timestamps`, the same conversion the initial booking uses), fare/currency, and a **re-stamped `details`** whose `airline`/`flight_number` keys remain the exclusion identity (so the next repair excludes the flight the traveler is actually on) with the original preserved under `details.rebooked_from` — and raises on a failed field write *before* the tool returns, so the cascade unit can never flip `fixed` over stale fields; the pages render that row, no client-side merging. Two accepted loosenesses (2026-07-16 evening replan): the write replaces `details` **wholesale** — **honored by Phase 33**: both stamping paths write the same `flight_options.details_from_option` dict under a key-set parity test, the repair adding only `rebooked_from` (which since Phase 33 also carries the original's `airline_name` for the was-line), so no future key can be wiped by a repair without a red test — and the bookings insert precedes the field write, so a failed field write strands an inert booking row while the repair honestly reports `error` (no rollback machinery at demo scale). **The rebooked flight must differ from the original** (Phase 31, from live QA): the flight re-shop hard-excludes the cancelled flight's `(airline, flight_number)` identity, falls back to an equal-depart+arrive-clocks tell when identity is absent (seed trips, pre-31 rows), and an exclusion that empties the pool reverts to the unfiltered closest-arrival pick with a warning — different where the cache allows, never a crashed repair. The **disruption injector** is live: `POST /v1/disruption/break_flight` flips a trip's flight to `broken` (idempotent, 404 without a flight item); `POST /v1/sabre_tools/seed_trip` and `POST /v1/sabre_tools/repair_trip` are the walkthrough/demo surface.
- **Concurrency pattern (Cascade Repairer) — proven 2026-07-07 by the Phase 5 spike; no rewire needed.** The reusable pattern lives in `backend/api/concurrency_core.py` and is what every voice phase builds on: background work fired with `asyncio.create_task` alongside the active session (never sequential `await` per tool), completions reported into a per-session event log, and agent turns staying a plain `await Runner.run(...)` on the same loop. A **session snapshot** of pending/landed background work is injected into the agent's instructions each turn so it can answer "how are the repairs coming?" by name — the wording must be marked authoritative or the model asks clarifying questions instead (measured; see `specs/2026-07-07-concurrency-spike/findings.md`). Two standing rules for later phases: **blocking GCP calls (BigQuery DML) inside async paths go through `asyncio.to_thread`** — a blocking write on the event loop would stall the very conversation this exists to keep alive; and the **session/event registry is deliberately in-process memory** — the demo runs a single Cloud Run instance, and external session state is out of scope for the hackathon. Both spike limitations closed in Phase 6 (2026-07-08): `_repair_one` now raises on a failed or 0-row `update_status`, so completion events report `error` instead of a false ok; and the deployed walkthrough proved five real `itinerary_items` rows flipping broken → repairing → fixed with fresh `updated_at` in ~35 seconds. Acceptance test passed verbatim, live on Cloud Run: *the agent responds while a fake 10-second API call is still in flight.*

- **Voice booking (Phase 17): guided multi-turn booking on the Concierge** — `book_trip` is retired; the flow is `search_flights` (since Phase 27, 2026-07-14: **InstaFlights** via the dispatcher's `instaflights_search` op — additive shapes, `airport_tz.py`'s static IATA→IANA table converting offset-less airport-local times to PT, best-effort supported-markets validation with a speakable redirect, additive `FlightOption.arrive_date` so a converted red-eye can't produce `end_ts < start_ts`; BFM's `flight_search` op remains only in `repair_tools.py` until Phase 29. Hardened by Phase 28 same day: the parser skips any itinerary touching an airport absent from `AIRPORT_TZ` — every segment's both ends, not just endpoints — and dedupes byte-identical itineraries by (flight number, times, price) before numbering; `_METRO_ALIASES` maps `NYC→JFK`/`WAS→IAD`/`CHI→ORD` server-side before the market check, with a matching `BASE_INSTRUCTIONS` clause; the mock emits airport-local clocks derived from its Pacific fiction so mock parses round-trip to the classic spread in any direction; and `AIRPORT_TZ` covers the **full live supported-markets list** (which carries metro and non-US codes — NYC, LON, PAR, EZE, …) under a cert-fenced parity test. Verified live on Cloud Run 2026-07-14: real fares spoken, mock rows written. Top 2–3 options stored per session in `_SESSION_FLIGHT_OPTIONS`, returned as a **speakable** numbered summary — prices rounded, airline *names* spoken ("Option one on Delta…"), codes and fare-class letters never. **Phase 33 rich fields:** `FlightOption` carries `airline_name` (static shared `AIRLINE_NAMES` table in `flight_options.py` — one copy, `itinerary_ui` imports it; unknown codes fall back to the bare code), `cabin` (notebook letter map), whole-journey `duration_minutes`, `layover_airports`, and `arrives_next_day` — all additive `Optional` upstream shape fields that **degrade to defaults, never skip an itinerary** (contrast the timezone check, which is correctness and still skips); both `details` stamping paths write the shared `details_from_option` dict; the tool result appends a bracketed on-request **reference block** (carrier + flight number, cabin, duration, connections) so the agent answers follow-ups without re-searching, and `BASE_INSTRUCTIONS` marks the bracket reference-only. Accepted looseness (Phase 33 close-out replan, 2026-07-16): a connecting itinerary is summarized from its **first segment's** marketing carrier and first fare-info cabin, so a codeshare or mixed-cabin connection reads as one carrier/cabin for the whole journey — demo-scale risk, the scripted anchor pair returns nonstops. A first-turn clause (PR #61, 2026-07-16) pins Vocal Bridge's automatic opening turn to a one-sentence greeting — the model may only say it's "pulling something up" when actually about to call a tool.) → `book_flight(option_number)` (creates the `Trip` + planned→booked flight `ItineraryItem` + `Booking` row whose `raw_response` carries the chosen option and its alternatives — the status endpoint's `detail` payload derives from it — then **replaces** the `_SESSION_TRIPS` pin and clears the options) → `complete_trip` (background task builds hotel/ground/dining/experience ~1.5s apart so cards materialize one by one on the 1.5s pollers). Every failure path returns a **speakable string** (standing rule). The mock Sabre client returns three deterministic itineraries per search so the options flow works in `SABRE_MODE=mock`. **Trip pinning (settled by Phases 18–19, 2026-07-12, superseding the earlier "confirm once" replan decision):** the latest-trip auto-pin is gone — a session pins a trip in exactly three ways: `book_flight` pins the trip it just created, the disrupt flow passes an explicit `trip_id` (the Phase 12 seam), or the caller sends an optional `trip_id` in the `/v1/web_call/query` POST body (Phase 19 — how the iOS app and `?trip_id=` pages pin the trip they're displaying). Pins are **pin-only-if-unpinned**: `ensure_trip_context` is cache-first, so a passed `trip_id` never clobbers an existing pin (a just-booked trip wins over the previously displayed one). Fresh sessions with no `trip_id` stay unpinned and get guided booking; `_today_line` injects today's Pacific date into the instructions so relative dates resolve. **Phase 23/31 additions:** the toolset gains **`trip_status`** — a fresh per-call repository read of the pinned trip's item statuses (never the cached pin or the snapshot), so "how's my trip?" answers honestly even when repairs ran under another session id, with no all-clear claim while anything is broken, repairing, *or cancelled*; `book_flight` stamps the chosen option into the flight item's `details` (since Phase 33 the full shared rich stamp; `airline`/`flight_number` remain the repair re-shop's exclusion identity, byte-identical to Phase 31); and during an `awaiting_consent` window for its pinned trip, `fix_trip` launches nothing and defers to the phone ("I'm already asking you on the phone — just say yes on the call and I'll get started.") — one consent channel at a time.
- **Destination info (Phase 35, shipped + QA'd 2026-07-16): the Concierge's sixth tool, `destination_info(question)`** — one trip-aware, read-only Tavily web lookup answering "what's happening there / things to do" live during the call (conversational only — no real hotel/dining/experience booking, ever; `complete_trip`'s mocked build-out is untouched). The pinned trip's destination(s) and dates garnish the query **server-side** via the cache-first `ensure_trip_context` (unpinned sessions search the question verbatim); the synchronous `TavilyClient` runs off the event loop (`asyncio.to_thread` inside an 8 s `wait_for` — the standing blocking-call rule), with `search_depth='basic'`, `include_answer=True`, `max_results=3`. The result passes the **`_speakable` sanitizer contract** (hardened by the Phase 35 close-out, PR #65, after independent validation caught bare `www.` URLs and Markdown surviving the original `https?://`-only pattern): Markdown links resolve to their text, protocol and bare-`www.` URLs drop, emphasis/code/heading marks drop, and the 600-char cap lands on a word boundary — never a mid-word slice into TTS. The tool is **always registered** (key or no key — lazy client, call-time `TAVILY_API_KEY` read, so importing `concierge.py` and the hermetic suite need no credentials), and every failure (missing key, Tavily error, timeout, empty results) returns one speakable apology; instructions make it a **subtle offer** (answer when asked, never pitch it unprompted, never read web addresses aloud). Deployment surface: `tavily-python` pinned in backend deps + `TAVILY_API_KEY` on Cloud Run (`--update-env-vars` merge, survives redeploys). Two accepted loosenesses (2026-07-16 replan): a timed-out lookup speaks the fallback while the underlying request **finishes out its worker thread** (`to_thread` can't cancel it — the single-operator demo never starves the pool), and key-less environments log a full warning traceback per question (the deployed service has the key; the traceback is wanted when something real breaks). Phase 34 (return-flight indication) reuses `_tavily_search` wholesale — the Tavily path stores nothing in session state, which is exactly why it can answer return questions without violating the never-book-once-booked rule.
- **Legal pages (Phase 16, expanded Phase 17): `GET /v1/legal/privacy` + `GET /v1/legal/support`** — the App Store Connect–required URLs, served as self-contained static HTML from `backend/api/assets/legal/` (read per request; `uvicorn --reload` doesn't watch HTML). Stable Cloud Run URLs, versioned in-repo, no new infra; content must stay accurate to what the backend actually does. The privacy policy now carries the App Review 5.1.1/5.1.2 disclosures (tested in `test_legal.py`): **all three processors named** (Vocal Bridge — voice; OpenAI — AI processing of conversation text; Google Cloud — storage), a **90-day retention** ceiling, **consent-withdrawal** instructions (the in-app About action), deletion within 30 days of request, and equivalent-protection language.
- **Access-code gate (Phase 17): `DEMO_ACCESS_CODE` protects the API, not just the UI** — `backend/api/access_gate.py` middleware requires an `X-Access-Code` header (compared with `secrets.compare_digest`) on everything under `/v1/`, with a small public allowlist: `/v1/legal/*`, `POST /v1/auth/validate` (`backend/api/auth.py`, the iOS first-launch check), and the five `GET` HTML page shells (`/v1/web_call/`, `/v1/mobile_voice/`, `/v1/itinerary/`, `/v1/demo/`, `/v1/booking/` — inert without the gated JSON APIs). **Fail-open when the env var is unset** (one startup-style warning) so local dev and hermetic CI need zero setup; the env var is read per request, so rotation is a `--update-env-vars` merge — every client re-gates on its next 401. All four pages read `?code=` (persisted to `localStorage`) and attach the header on every fetch; it's a shared demo secret (App Review notes + judges), not a security boundary.
- **Demo orchestrator — shipped 2026-07-10 (Phase 12), reworked into the consent-gated flow by Phases 23/31 (live-QA'd 2026-07-15):** `/v1/demo` (`backend/api/demo.py`) composes the beats from existing seams — `create_seed_trip`, `break_trip_flight`, `launch_trip_repairs`, `vb_cli.place_call`, the `outbound_call.py` scrub/env helpers. **`POST /disrupt` does exactly two things**: places Call 1 (a consent-asking script composed from the real pinned trip's data at placement time — `call_purposes.py`, pure functions over loaded models) and breaks the flight; **no repairs launch at click time**. A background **consent watcher** polls the VB session log for Call 1, reads the traveler's answer from `transcript_text`, classifies it with a minimal Agents SDK call (`CONSENT_LLM_MODEL`, default `gpt-5.4-mini`; empty transcript, API failure, or an off-script answer all read *ambiguous*), and launches the cascade **only on an unambiguous yes** — the grant is atomic (`consent.resolve` before `launch_trip_repairs`, no awaits between) so a re-clicked Cancel supersedes a stale watcher via tokens instead of double-launching. On the landed repairs the completion watcher places **Call 2**, its purpose composed from the actual post-repair `detail` data. The wait's state lives in the in-process **consent registry** (`consent.py`) and reaches the page as an additive best-effort `consent` block on the status poll. **The session-log join key is `room_name`** (hard-won live 2026-07-15): `vb call` returns `call_id` + `room_name`, but `vb logs list` rows carry only `id` + `room_name` — `place_call`'s sanitized payload therefore includes `room_name` (a session identifier, not a transport secret) and `find_session` matches `id`/`session_id`/`room_name`; a watcher keyed on `call_id` polls to its 180 s timeout while the completed session sits in the log. Standing invariants (tested): the outbound call fires before any data **write** (reads may precede it — the script needs the trip; a trip that can't break 404s *before* any quota is spent), and no payload ever carries the callee number or API key.

## Data

- **BigQuery** for structured data (via `backend/api/helpers/bigquery_helper.py`): dataset `vocal_bridge` in `us-west1`. The helper is a config-driven client with parameterized `run_select` and `run_dml` primitives; the typed repository layer (Phase 3) lives in `backend/api/repositories/` — pydantic models + one module per table, statuses validated as Python enums at the repository boundary (BigQuery has no enum type).
- **Table ids are config-driven**: `config.yaml` `metadata:` carries a `<name>_table_id` per table (donor-project pattern). The same entries feed CI table creation (via `image.env` → `run_artifact_setup.sh`) and runtime table references (`bq_helper.get_table_reference`), so setup and runtime can never disagree; a missing entry fails the test suite.
- **Writes are query-job DML, never streaming inserts** — rows in the streaming buffer can't be UPDATEd for up to 90 minutes, which would break the demo's booked → broken → repairing → fixed status flips seconds apart. Demo-scale volume makes DML cost irrelevant.
- **Timezone discipline (standing rule, Phase 19, 2026-07-12): the database stores UTC; the edges speak Pacific.** BigQuery `TIMESTAMP` holds honest UTC instants only — mock wall-clock fiction is *declared* Pacific at ingest (`ZoneInfo("America/Los_Angeles")`, the `_PACIFIC` constants in `concierge.py`/`sabre_tools.py`) and converts on write; every user surface renders `America/Los_Angeles` explicitly, labeled "PT" (never "PST" — it's PDT in July), never browser/device-local. iOS renders no clock times (audited: `start_ts`/`end_ts` decoded but unused). The InstaFlights offset-less variant of the real-Sabre conversion edge is **closed** (Phase 27: `backend/api/sabre/airport_tz.py` localizes each end at its own airport and converts to PT; an unmappable airport skips the itinerary — since Phase 28 checked on **every segment's both ends**, and the mock emits airport-local clocks so mock parses round-trip correctly in either direction). The BFM offset-bearing variant is moot — BFM has no content on this PCC and the entitlement-ask route was closed 2026-07-14. The Phase 27 residuals (endpoint-only parser check, mock clock re-interpretation) were closed by Phase 28 on 2026-07-14; `AIRPORT_TZ` parity with the live supported-markets list is now guarded by a cert-fenced test.
- **GCS** for audio recordings and artifacts (via `backend/api/helpers/gcs_helper.py`): bucket `vocal-bridge-hackathon-audio` (us-west1, uniform access).
- Both helpers read project/dataset/bucket names from `backend/config.yaml` (overridable by env vars) and create their GCP clients lazily — importing them, and therefore running the test suite, requires no credentials.

### Schema (BigQuery)

**Core trip tables**
- `trips` — trip_id, user_id, title, status (draft/booked/active/complete), origin, destination(s), start_date, end_date, created_at.
- `itinerary_items` — item_id, trip_id, type (flight/hotel/ground/dining/experience), status (**planned/booked/broken/repairing/fixed/cancelled** — the repair lifecycle drives both the agent's cascade logic and the live UI), provider (sabre/other), provider_ref, start_ts, end_ts, location, details (JSON), price, currency, updated_at.
- `bookings` — booking_id, item_id, trip_id, sabre_confirmation_ref, state (pending/confirmed/cancelled), booked_at, raw_response (JSON).

**Conversation logging**
- `sessions` — session_id, trip_id, architecture (cascaded/realtime/concierge), client (vb_web), started_at, ended_at.
- `turns` — turn_id, session_id, role (user/agent), transcript, audio_gcs_uri, started_at, ttfb_ms, duration_ms.

**Evaluation metrics**
- `eval_runs` — run_id, architecture, git_sha, scenario, ttfb_ms, e2e_latency_ms, wer, mos_estimate, notes, run_at.

## Testing

- **pytest** for API and agent unit/integration tests (`backend/tests/`, config in `backend/pytest.ini`), run in CI on every Cloud Build **inside the built container** — the exact artifact that ships. Tests must stay hermetic: no GCP credentials, no `OPENAI_API_KEY`; GCP interactions are mocked at the helper boundary.
- **Exception with a fence — the `cert` marker (Phase 25, hardened Phase 26):** live Sabre CERT tests (`backend/tests/test_sabre_cert.py`) are deselected by default (`addopts = -m "not cert"`), so CI and bare local runs never touch the network. Run deliberately with the raw credential pair passed through `docker compose exec -e` (command at the top of the test module); several tests are **tripwires** that assert documented entitlement gaps and fail loudly if Sabre's behavior changes. Phase 26 hardening: the create tripwire recovers the raw response from the pydantic `ValidationError` (error `input`), asserts the `UNAUTHORIZED_ACCESS` marker across both `errors[]` fields, and cancels any harvested PNR in `finally` — a guarantee certified **hermetically** in `test_sabre_cert_cleanup.py` (fake clients, no `cert` marker, runs in every bare suite). Travel dates in cert tests and probes are always computed (`date.today() + timedelta`), never literals. The exploration probes carry meaningful exit codes: `sweep.py` exits nonzero on any `NETWORK-ERR`, `booking_lifecycle.py` on entitlement drift. The docs-contract suite (`test_validator_docs_contract.py`, including the `sabre-cert-notes.md` headings test) runs from a **full checkout** and deliberately skips inside the backend image, where repo-root files don't exist.
- **Voice evaluation harness** (course L5 patterns) run on demand: TTFB/latency, WER against ground-truth transcripts, MOS-style quality checks per architecture, results persisted to `eval_runs`. **Persisted runs go through the Cloud Run job `vocal-bridge-eval-harness`** (us-west1, deployed image + `gemini-service-account`) — the standing no-local-creds path per Josh's decision: `gcloud run jobs execute vocal-bridge-eval-harness --region us-west1 --wait` (update the job's image tag / `GIT_SHA` env after deploys). Local `make eval` without creds still measures but fails the write — use `--dry-run` locally.

## Deployment & CI/CD

- **Google Cloud Platform**, project **`vocal-bridge-hackathon`**, everything in **`us-west1`** (nearest full-featured region to the Mountain View event — West Coast serving minimizes live-demo latency).
- **Cloud Run** hosts the backend as `vocal-bridge-be-dev`, running as `gemini-service-account@vocal-bridge-hackathon.iam.gserviceaccount.com` (holds BigQuery/GCS/deploy roles). **The single-instance guarantee is the service-level cap** `run.googleapis.com/maxScale: '1'` (verified 2026-07-15) — it protects every in-process registry (consent, sessions, options, search log); the revision-level `autoscaling.knative.dev/maxScale: 100` annotation is a cosmetic default that does **not** override it, and "fixing" that knob is the actual operator hazard.
- **Cloud Build** CI/CD driven by `backend/config.yaml` + `backend/devops/cloudbuild.yaml` (all steps run with `dir: backend`): validate config → ensure BigQuery dataset → build/push image to Artifact Registry (`vocal-bridge-be-artifacts-dev`) → **pytest inside the built image** (a failure blocks the deploy) → deploy. The deploy uses `--update-env-vars` (merge), so env vars set once on the service — e.g. `OPENAI_API_KEY` — survive redeploys.
- **Trigger flow**: work happens on `vb/feature/<feature-name>` branches and lands on `vb/dev` by GitHub PR. The `vocal-bridge-be-pr-to-dev` trigger is a **push-to-branch trigger on `^vb/dev$`** (observed 2026-07-08): it fires on any push to `vb/dev`, including direct pushes and PR merges. Webhook deliveries can occasionally be missed — if a merge doesn't build, re-run manually: `gcloud builds triggers run vocal-bridge-be-pr-to-dev --branch=vb/dev`. **PR evidence — retired as a merge gate (decision, 2026-07-16 evening replan)**: the Phase 31 guard was deliberately removed from `git_pull_dev.sh` by commit `933f8e8` after it produced recurring acceptance-package (DoD-B) validation failures without ever catching a behavior defect; the script now uses the commit message as the PR body, or `PR_BODY.md` (repo root, gitignored) verbatim, never clobbering a hand-written body. The standing convention: **run evidence (mock walkthrough, live run, pytest output) lives in each phase's spec directory and its changelog entry, not the PR description** — future `validation.md` files must not require PR-body evidence sections.
- **Provisioning**: one-time project setup (APIs, service account + IAM, Artifact Registry repo, GCS bucket, BigQuery dataset) is scripted in `backend/devops/scripts/gcp_project_setup.sh` (idempotent); console-only steps (GitHub connection, trigger creation) are documented in `backend/devops/README.md`. BigQuery **tables** are created by CI on every build: the `setup-artifacts` step (`run_artifact_setup.sh`) ensures the dataset, then runs `backend/promotion_scripts/create_vocal_bridge_tables.sh` with the table ids from `config.yaml` metadata. Creation is idempotent and existing tables are **never dropped** — trip data survives deploys; a schema change requires a manual `bqtk.py drop-table --force` first.
- **Deployment health**: `GET /v1/hello/gcp_check` on the deployed service verifies BigQuery and GCS reachability, reporting each half independently.
