# Requirements — BigQuery Data Layer

Phase 3 of the roadmap. Stand up the six-table schema from `specs/tech-stack.md` as `bqtk.py`-based creation scripts, replace the donor project's leftover table scripts, and wire the existing helpers into typed repository functions that the agents, API, and later phases (concurrency spike, Sabre tools, live itinerary UI) consume without touching raw SQL.

## Scope

**In scope (full layer, confirmed by Josh):**

- Schema YAMLs + creation scripts in `backend/promotion_scripts/` for **all six tables**: `trips`, `itinerary_items`, `bookings`, `sessions`, `turns`, `eval_runs` — created in the existing `vocal_bridge` dataset via the donor `bqtk.py` CLI (kept as-is).
- Delete the donor table scripts and schema YAMLs parked in `backend/promotion_scripts/`: `create_spreadsheet_conversions_table.sh`, `create_rag_embeddings_table.sh` + `rag_embeddings_schema.yaml`, `create_blonter_msg_history_table.sh` + `blonter_msg_history_schema.yaml`, `create_bq_monitoring_table.sh`, `run_setup.sh`. Rewrite `promotion_scripts/README.md` for this project. (`bqtk.py` and `create_gcs_bucket.sh` stay — both are live.)
- **Typed repository functions for all six tables** in a new `backend/api/repositories/` package, with pydantic models per table and the write primitives added to `bigquery_helper.py` that they need (DML insert/update alongside the existing `run_select`).
- `itinerary_items.status` carries the full repair lifecycle (`planned/booked/broken/repairing/fixed/cancelled`) plus `updated_at`; the repository exposes a status-transition function since that drives both the cascade logic (Phase 4/5) and the live UI (Phase 9).
- pytest coverage for the repository layer with the BigQuery client **mocked at the helper boundary** — hermetic, no credentials, runs in the CI container.
- `gcs_helper.py` wiring limited to what the data layer defines: the `turns.audio_gcs_uri` convention (`audio/<session_id>/<turn_id>.wav`) exposed as a typed path builder — no new GCS operations.

**Out of scope:**

- Any agent, voice, or Sabre feature work — Phases 4+ consume this layer.
- The disruption injector endpoint (Phase 5) and trip-status endpoint / SSE (Phase 9).
- Real-BigQuery integration tests — tests stay hermetic per `specs/tech-stack.md` § Testing; the manual validation walkthrough covers the real dataset once.
- Schema migration tooling — tables are created fresh; if a schema changes pre-hackathon, drop and recreate via `bqtk.py`.

### Tables and fields

Types follow BigQuery standard SQL. All ids are STRING (UUID4 generated by the repository layer). JSON columns use the native `JSON` type; timestamps are `TIMESTAMP`.

| Table | Fields |
|---|---|
| `trips` | trip_id STRING, user_id STRING, title STRING, status STRING (draft/booked/active/complete), origin STRING, destinations STRING REPEATED, start_date DATE, end_date DATE, created_at TIMESTAMP |
| `itinerary_items` | item_id STRING, trip_id STRING, type STRING (flight/hotel/ground/dining/experience), status STRING (planned/booked/broken/repairing/fixed/cancelled), provider STRING (sabre/other), provider_ref STRING, start_ts TIMESTAMP, end_ts TIMESTAMP, location STRING, details JSON, price FLOAT64, currency STRING, updated_at TIMESTAMP |
| `bookings` | booking_id STRING, item_id STRING, trip_id STRING, sabre_confirmation_ref STRING, state STRING (pending/confirmed/cancelled), booked_at TIMESTAMP, raw_response JSON |
| `sessions` | session_id STRING, trip_id STRING, architecture STRING (cascaded/realtime/concierge), client STRING (vb_web), started_at TIMESTAMP, ended_at TIMESTAMP |
| `turns` | turn_id STRING, session_id STRING, role STRING (user/agent), transcript STRING, audio_gcs_uri STRING, started_at TIMESTAMP, ttfb_ms INT64, duration_ms INT64 |
| `eval_runs` | run_id STRING, architecture STRING, git_sha STRING, scenario STRING, ttfb_ms FLOAT64, e2e_latency_ms FLOAT64, wer FLOAT64, mos_estimate FLOAT64, notes STRING, run_at TIMESTAMP |

Status/enum values are validated in the repository layer (pydantic `Literal`/enum), not in BigQuery — BQ has no enum type and CHECK constraints would complicate `bqtk.py` creation.

## Decisions

- **Follow donor patterns** (Josh): `bqtk.py` stays untouched as the creation CLI; each table gets a `<table>_schema.yaml` (the format `bqtk.py --field-yaml-file` already parses, incl. `field_mode: REPEATED` for `trips.destinations`) plus the donor-style per-table wrapper, collapsed into a single idempotent `create_vocal_bridge_tables.sh <project_id> <dataset_id>` that creates all six — one command for setup and dress-rehearsal rebuilds. `bigquery_helper.py` keeps its conventions: config-driven, lazy client, never-raise `Tuple[bool, ..., Optional[str]]` returns.
- **DML inserts/updates, not streaming inserts.** Repository writes go through query-job DML (`INSERT`/`UPDATE` with query parameters), not `insert_rows_json`. Rows in the streaming buffer can't be UPDATEd for up to 90 minutes — that would break the demo's core move, flipping `itinerary_items.status` booked → broken → repairing → fixed seconds apart. Demo-scale volume makes DML cost/quota irrelevant.
- **Repository shape**: one module per table in `backend/api/repositories/` (`trips.py`, `itinerary_items.py`, `bookings.py`, `sessions.py`, `turns.py`, `eval_runs.py`) plus `models.py` with the pydantic models and status enums. Functions cover what later phases need: create, get-by-id, list-by-parent (items/bookings by trip, turns by session), and targeted updates — most importantly `itinerary_items.update_status(item_id, status)` which also stamps `updated_at`, and `trips` status updates. No deletes; cancellation is a status.
- **Mocked-client pytest** (Josh): tests patch the helper's lazy `client` property/attribute and assert generated SQL, query parameters, row-to-model mapping, and error tuples. No GCP credentials, no network — matching `tech-stack.md` "GCP interactions are mocked at the helper boundary" and the CI step that runs pytest inside the built container.
- **Enum validation lives in Python** (pydantic) so invalid statuses fail fast at the repository boundary with a clear error, keeping the BigQuery schema plain.
